# AgroChain — data contracts v1

Status: Stage 1 normative specification, not an implemented API or chaincode. Every JSON example is synthetic. Only the explicitly identified signature/commitment vector is cryptographically verifiable; transaction IDs in examples are illustrative, not evidence of commits. Storage destinations are fixed by [security and privacy](SECURITY_AND_PRIVACY.md).

## Common encoding and validation

Use UTF-8 JSON and exact schema identifiers `agrochain.<record-type>.v1`. Reject unknown versions, unknown fields, duplicate object keys, invalid Unicode, nulls, non-finite numbers, exponent/fraction syntax for integer fields, leading zeros, negative zero, and coercions from numeric strings. Optional fields are omitted, never null. Strings must already be Unicode NFC; reject non-NFC rather than silently changing signed content. No floating-point financial calculations. Internal multiplication/division uses checked integers or arbitrary precision; Java `BigDecimal` is permitted for display, never a substitute for specified exact comparisons.

| Type / field convention | Definition |
| --- | --- |
| ID | ASCII `^(BAT|LOT|DOC|TRF|CST|RPT|ANM|OP|CFG)-[A-Z0-9]{8,32}$`; prefix matches record kind. Allocate at least 128 random bits in new runtime IDs, encoded uppercase base32 without padding. Fixed readable IDs in this document are test fixtures only. |
| MSP | Exact enum `ProducerMSP`, `LogisticsMSP`, `RetailerMSP`, `RegulatorMSP`; ordering identity cannot submit domain commands. |
| Reference string | ASCII `[A-Z0-9_]{1,64}` for issuer/key/reviewer references; no personal identifiers. Source registry restricts values further. |
| `quantityGrams` | JSON integer 1–100,000,000 inclusive; immutable per batch; 1 kg = 1,000 g. UI may render kg with at most three decimal places. |
| `priceKurusPerKg`, `offeredPriceKurusPerKg`, purchase/retail anomaly rates | JSON integer 0–1,000,000,000 inclusive; purchase must be strictly positive. 1 TRY = 100 kuruş. |
| `totalKurus`, `freightTotalKurus` | JSON integer 0–1,000,000,000,000 inclusive. Purchase invoice total must be positive and satisfy `priceKurusPerKg * quantityGrams = totalKurus * 1000` exactly; reject sub-kuruş residuals. |
| `currency`, `taxBasis` | Exact values `TRY`, `EXCLUDING_TAX`. No discounts or tax computation. Reject mixed basis rather than adjusting it implicitly. |
| `issuedAt`, `reportedAt` | Exact UTC `YYYY-MM-DDTHH:mm:ss.SSSZ`, valid calendar time, no leap seconds. These are attributed declarations, not trusted lifecycle clocks. |
| `harvestDate` | Valid `YYYY-MM-DD`, source-declared; no automated freshness/legal claim. |
| `txTime` | Object `{ "seconds": "1789549200", "nanos": 0 }`; seconds is canonical nonnegative decimal string (Fabric int64, no loss through JS number), nanos integer 0–999,999,999. Derived from transaction context only. |
| `txId` and named transaction references | 64 lowercase hex characters; obtained from Fabric for persisted records. Never accepted as authority from a command body. |
| Nonce / salt | 32 bytes represented as 64 lowercase hex characters; generated by a cryptographically secure random generator outside chaincode, fresh per new source document / commitment / PDC record. |
| Signature / public key | Unpadded base64url; Ed25519 signature decodes to 64 bytes, raw public key to 32 bytes. Strict decoding, no alternative alphabets/padding. |
| `version`, `expectedVersion`, `resultVersion` | Integer 0–2,147,483,647; create expects 0, persisted version starts at 1; increment without wrapping. |
| `thresholdBps` | Integer 0–100,000; 100 basis points = 1%; default 5,000. |
| `increaseBps` | Signed integer derived with mathematical floor, including negative values; not client authoritative. |

All normalized documents are at most 64 KiB after canonicalization. Attachments are at most 5 MiB. The source-document batch/operation binding and field equality checks are mandatory even if a signature is valid.

## Commands and receipts

Every command uses this envelope. `payload` is an operation-specific object defined below; source documents/openings and commercial values go in the transient map, not in `payload`.

```json
{
  "schemaVersion": "agrochain.command.v1",
  "operationId": "OP-ACCEPT01",
  "batchId": "BAT-NORMAL01",
  "expectedVersion": 2,
  "command": "AcceptPickup",
  "payload": {
    "transferId": "TRF-PICKUP01",
    "quantityGrams": 100000
  }
}
```

| Command | Required public `payload` fields | Required transient inputs |
| --- | --- | --- |
| CreateBatch | `productCode`, `gradeCode`, `quantityGrams`, `originRegionCode`, `harvestDate`, `logisticsMsp`, `intendedRetailerMsp` | `evidence`: one CKS bundle |
| OfferPickup | `transferId`, `quantityGrams` | `evidence`: one purchase invoice, one HKS and one UETDS bundle |
| AcceptPickup / AcceptDelivery | `transferId`, `quantityGrams` | None |
| OfferDelivery | `transferId`, `quantityGrams` | None; references previously accepted batch manifest |
| RecordFreightCost | `costId` | `evidence`: one freight invoice; `recordSaltHex` |
| ReportRetailPrice | `reportId`, `retailLotId`, `policyId` | `retailReportInput`: `offeredPriceKurusPerKg`, `currency`, `taxBasis`, `reportedAt`, `recordSaltHex`; other fields derived from committed batch/evidence |
| EvaluatePrice | `anomalyId`, `reportId` | `proposedResult`: `increaseBps`, `classification`, `reasonCode`; `recordSaltHex`; authoritative monetary inputs read from PDCs |
| OpenReview | `anomalyId` | `reviewActionInput`: `reviewerRef`, `recordSaltHex`; separate `reviewStateSaltHex` |
| ResolveReview | `anomalyId` | `reviewActionInput`: `reviewerRef`, `outcome`, `explanation`, `recordSaltHex`; separate `reviewStateSaltHex` |

The transient map values are UTF-8 canonical JSON bytes; `recordSaltHex` and `reviewStateSaltHex` are themselves JSON strings. `evidence` is an array of `{envelope, body, saltHex}` objects sorted by `envelope.header.documentId`; reject duplicate entries and extra evidence types. Original attachment bytes stay off-chain. Every required field is mandatory unless explicitly designated optional. Output metadata (`actorMsp`, `txId`, `txTime`, versions) is derived in chaincode, never copied from asserted caller fields.

Immutable operation receipt fields: `schemaVersion=agrochain.receipt.v1`, `operationId`, `batchId`, `command`, `actorMsp`, `txId`, `txTime`, `resultVersion`, `objectIds` (array of created/referenced opaque IDs, sorted, unique). Key by MSP + operationId and index by batch + resultVersion. Replay always rejects with `DUPLICATE_TRANSACTION`; a backend status lookup may return the original receipt as recovery, labeled as already committed rather than a new submission. Private request digests, if retained for conflict diagnostics, reside only in the appropriate PDC or controlled off-chain operation store.

For transfers, costs, retail reports, anomalies and review actions, obtain recorded execution time through their transaction references and the corresponding receipt's `txTime`. Preserve both offer and acceptance transaction references for handoffs. Do not invent additional authoritative timestamps from document dates or backend response time.

Retail lot shared record: `schemaVersion=agrochain.retail-lot.v1`, `retailLotId`, `batchId`, `quantityGrams`, `retailerMsp`, `reportId`, `txId`. It is immutable and created with the report. The lot index is unique in both directions. No parent/child batches, many-to-many document allocation or shrinkage accounting are accepted in v1.

## Signed source documents

A bundle is `{envelope, body, saltHex}`. Only `envelope` goes to shared ledger. `body` and `saltHex` are an authorized opening: purchase → trade PDC, freight → freight PDC, other institutional assertions → controlled off-chain archive. Backend sends each opening transiently so chaincode can independently verify its commitment and required fields.

`envelope` contains exactly `header` and `signature`. Every header field shown below is required. `sourceSystem` is `CKS|EFATURA|HKS|UETDS`; `sourceMode` is exactly `SIMULATED` in v1. `issuerId` and `keyId` must be registered for that system and type. `sourceDocumentId` is an opaque source-side ID matching the DOC grammar; it is distinct from any natural invoice number. The issuer must return the same bundle for a retried bound operation; it must not mint a new nonce to bypass replay checks.

`eligible` and `notified` are JSON booleans. Negative simulator assertions may be signed for tests but cannot authorize their consuming commands (`SOURCE_CLAIM_REJECTED`). All normalized noninvoice bodies are themselves archived as canonical JSON; they need no attachment field. Invoices attach synthetic raw XML, JSON or PDF, constrained to `application/xml`, `application/json`, `application/pdf` and a 64-lowercase-hex SHA-256 digest. Raw attachment bytes, file paths and the bare attachment digest are never public fields. Stage 5 fixtures need complete bundles for all four adapters and both invoice types.

## Canonical commitment and signing protocol

Canonicalize with [RFC 8785 JSON Canonicalization Scheme](https://www.rfc-editor.org/rfc/rfc8785.html), after the stricter validations above. JCS supplies deterministic member ordering, JSON string escaping and number representation; it does not normalize Unicode. Object key order and insignificant whitespace do not change a commitment. Array order does: schema-defined arrays must be sorted as stated before signing, and invalid ordering is rejected rather than silently repaired. Do not hash pretty-printed JSON or use language-default map serialization.

Define byte concatenation `||`; all literal domain strings below are UTF-8/ASCII and end in exactly one zero byte (`\0`), not the two visible characters backslash and zero. `U64BE(n)` is exactly eight unsigned big-endian bytes.

```text
B = UTF8(JCS(body))
S = HEX_DECODE(saltHex)                         // exactly 32 secret random bytes
C = SHA256(UTF8("AgroChain/document/v1\0") || S || U64BE(len(B)) || B)
header.commitment = LOWERCASE_HEX(C)
M = UTF8("AgroChain/source-signature/v1\0") || UTF8(JCS(header))
signature = BASE64URL_NO_PADDING(Ed25519_SIGN(sourcePrivateKey, M))
```

Sign the complete header, including commitment and algorithm names; do not include `signature` in `M`. Use pure Ed25519, not Ed25519ph or a homegrown prehash variation, according to [RFC 8032](https://www.rfc-editor.org/info/rfc8032/). Public key selection comes only from the ledger registry for `(issuerId,keyId)`, never an untrusted key embedded in a request.

Verification order: validate schema and limits; resolve trusted enabled key/system/type; verify signature; check batch/operation/source-mode binding; compute `C` from the authorized opening and compare; enforce body business fields and source replay indices. For an original file, independently recompute SHA-256 of its exact bytes and compare to the signed body's attachment digest. A newline or encoding change in an XML/PDF attachment counts as a changed document; attachments are not reserialized. Only backend verification handles attachment bytes; chaincode verifies the committed normalized assertion and digest, not the semantic contents of an external file it cannot read.

A verification response uses `schemaVersion=agrochain.integrity-result.v1`, `documentId`, `commitmentMatched`, `signatureVerified`, `attachmentMatched` (only for attached documents), `sourceMode`, `verifiedAt` (backend observation), and `committedTxId`. Return these success booleans only after checking against the stored original envelope; failure uses the error envelope below. Integrity queries do not mutate lifecycle state or re-consume documents.

### Public test vector, never runtime secrets

For the exact invoice/body above:

- `saltHex = 202122232425262728292a2b2c2d2e2f303132333435363738393a3b3c3d3e3f`
- Raw attachment UTF-8, no trailing newline: `<invoice id="SIM-001">200000</invoice>`
- Canonical body length: 288 bytes; length prefix: `0000000000000120`.
- Commitment: `4e1259fa1bf2ab64d37e9026c276fbe2dc06872f2deb800cbc87f83ffd15940a`.
- Raw Ed25519 public key, base64url: `njeHGEyz0EF6HP6iEDUHPftD5gwevFdrlCcOnJgTFkY`.

A reviewer can reproduce a live commitment only if authorized to receive the body and secret salt; the public hash alone is not an opening. Hashing is not encryption.

All anomaly fields below are required and private. Inputs are derived from the committed purchase, report and freight cost. `ruleVersion=price-increase-v1`. `classification` is `NO_SIGNAL|REVIEW_REQUIRED`; corresponding reason is `WITHIN_PILOT_THRESHOLD|ABOVE_PILOT_THRESHOLD`. Review state is `NOT_REQUIRED` for NO_SIGNAL, otherwise `OPEN|IN_REVIEW|RESOLVED`. `increaseBps` uses mathematical floor; compare exact integer products to classify (see [product scope](PRODUCT_SCOPE.md)).

```json
  "anomalyId": "ANM-NORMAL01",
  "batchId": "BAT-NORMAL01",
  "reportId": "RPT-NORMAL01",
  "policyId": "CFG-PRICE001",
  "ruleVersion": "price-increase-v1",
  "purchasePriceKurusPerKg": 2000,
  "retailPriceKurusPerKg": 2800,
  "freightTotalKurus": 20000,
  "quantityGrams": 100000,
  "increaseBps": 4000,
  "thresholdBps": 5000,
  "classification": "NO_SIGNAL",
  "reasonCode": "WITHIN_PILOT_THRESHOLD",
  "reviewState": "NOT_REQUIRED",
  "recordSaltHex": "808182838485868788898a8b8c8d8e8f909192939495969798999a9b9c9d9e9f",
  "operationId": "OP-EVAL0001",
  "txId": "1111111111111111111111111111111111111111111111111111111111111111"
}
```

For the suspicious scenario, substitute retail=3700, increaseBps=8500, classification=REVIEW_REQUIRED, reasonCode=ABOVE_PILOT_THRESHOLD and initial reviewState=OPEN with distinct IDs/salts. The shared evaluation record contains only `schemaVersion=agrochain.evaluation-reference.v1`, `batchId`, `reportId`, `anomalyId`, `txId`. It must not include a threshold result hash that is deterministic over a small set of outcomes without a secret salt.

Private review action fields: `schemaVersion=agrochain.review-action.v1`, `operationId`, `anomalyId`, `action=OPEN_REVIEW|RESOLVE_REVIEW`, opaque `reviewerRef`, fresh `recordSaltHex`, `txId`. For resolution, additionally require `outcome=EXPLAINED|FOLLOW_UP_RECOMMENDED|INSUFFICIENT_EVIDENCE` and `explanation` (1–2,000 characters, no PII); these fields are absent for opening. The original anomaly scoring fields, evaluation operationId and txId stay immutable. Only its `reviewState` and `recordSaltHex` change on review: take the new anomaly-record salt from `reviewStateSaltHex`, independently of the action's salt. Append-only actions preserve the review history; no separate low-entropy private status value is written.

Policy record fields: `schemaVersion=agrochain.price-policy.v1`, `policyId`, `ruleVersion`, `thresholdBps`, `currency=TRY`, `taxBasis=EXCLUDING_TAX`, `comparison=STRICT_GREATER`, `createdTxId`. One immutable bootstrap policy in v1. New thresholds require new policy IDs and a future governed configuration change, never rewriting the meaning of a prior result.

Source-key record fields: `schemaVersion=agrochain.source-key.v1`, `issuerId`, `sourceSystem`, `documentTypes` (sorted unique array of allowed types), `keyId`, `publicKeyRawBase64url`, `enabled` (boolean), `createdTxId`. Registry keys are scoped by issuer and key ID; an EFATURA key cannot authorize CKS claims. No private key or arbitrary external key URL belongs in this record.

## Storage keys, queries and public projection

Use Fabric composite keys rather than concatenating unescaped user input. Shared object types: `batch(batchId)`, `lot(retailLotId)`, `transfer(transferId)`, `document(documentId)`, `sourceUse(issuerId,sourceDocumentId)`, `nonceUse(issuerId,nonce)`, `operation(actorMsp,operationId)`, `history(batchId,zeroPaddedVersion)`, `evaluation(reportId)`, `policy(policyId)`, `sourceKey(issuerId,keyId)`. History versions use exactly ten decimal digits, padded on the left with zeros. The source-use values reference the consuming batch, operation and transaction; they contain no commercial values. Every create checks key absence before writing; transaction version conflicts are handled at commit.

Maintain shared references for the batch's accepted CKS/invoice/HKS/manifest IDs, freight cost ID and report ID in `batchEvidence(batchId)`; only append a previously absent slot, never replace an accepted document. Its value fields are `schemaVersion=agrochain.batch-evidence.v1`, `batchId`, and optional `cksDocumentId`, `purchaseDocumentId`, `hksDocumentId`, `transportDocumentId`, `freightCostId`, `retailReportId`. These opaque references are shared, but not consumer fields. All command evidence checks use these committed references rather than caller-selected arbitrary PDC keys.

Private keys: `documentOpening(documentId)` in the proper trade/freight collection stores exactly `{body,saltHex}`; `cost(costId)` in freight; `report(reportId)`, `anomaly(anomalyId)`, and `reviewAction(anomalyId,operationId)` in retail audit. Serialize the complete private values with JCS, including their secret salt. For a stored opening the random `saltHex` already provides entropy; separate domain records have `recordSaltHex`. Do not write unsalted copies or private amount-only indices. Document envelope/body version supplies the opening schema; records carry their own versions.

Shared queries: `GetBatch`, `GetBatchHistory`, `GetTransfer`, `GetOperation`; private queries: `GetPurchase`, `GetFreightCost`, `GetRetailReport`, `GetAnomaly`, `GetReviewHistory`. The relevant ID/batch must belong to the caller's allowed route, and private queries enforce the collection and role matrix. No generic arbitrary-key/private-collection API is exposed. An authorized requester missing private bytes receives PRIVATE_DATA_UNAVAILABLE, even if the shared hash exists.

Consumer response `schemaVersion=agrochain.public-trace.v1` allowlist: `retailLotId`, `batchId`, `productCode`, `gradeCode`, `quantityGrams`, `originRegionCode`, `harvestDate`, `state`, `version`, `organizations` (fixed `{role,displayName}` items), `history` (only creation and accepted handoff `{eventType,fromRole,toRole,recordedAt,txId}` items; fromRole omitted for creation), `sources` (`{sourceSystem,sourceMode,verificationStatus}`), `asOfBlock` (canonical decimal string) and `updatedTxId`. `verificationStatus=SIGNED_SIMULATOR_ASSERTION` describes verified normalized evidence, not physical truth. Empty/missing lot returns 404; stale projections report their checkpoint and are never supplemented with private serializers. Public roles are `PRODUCER|LOGISTICS|RETAILER`; strings are fixed from configuration rather than personal free text. No other nested field is allowed.

## Errors and transaction outcomes

Error shape, excluding secrets and internal exception text:

```json
{
  "schemaVersion": "agrochain.error.v1",
  "code": "DOCUMENT_ALREADY_USED",
  "message": "This source document has already been consumed.",
  "operationId": "OP-OFFER002",
  "correlationId": "REQ_DEMO0001",
  "retryable": false
}
```

`operationId` is omitted when unavailable or malformed; `correlationId` uses the reference-string grammar. These error fields are the complete allowed response; no PDC body, stack trace, certificate or arbitrary exception message. IDs in errors are scoped to the authenticated caller to avoid existence disclosure.

| HTTP status | Stable domain codes / meaning |
| --- | --- |

Unknown commit outcome is **not a confirmed failure or success**. Return HTTP 202 with `schemaVersion=agrochain.operation-status.v1`, `operationId`, `status=SUBMITTED_UNKNOWN`, optional known `txId`, and `statusUrl`; no success receipt. Status lookup reports `PENDING|SUBMITTED_UNKNOWN|COMMITTED|FAILED` with a receipt only for COMMITTED or a sanitized error for FAILED. HTTP 201 with receipt means a new valid committed mutation; HTTP 200 is used for query/recovery, not to disguise a failed blockchain operation.
